## Módulo administrativo completo (4 agentes en paralelo)

Juan Camilo pidió avanzar todo el módulo admin con varios agentes a la vez. Se lanzaron 4 agentes `general-purpose` en paralelo, cada uno dueño de carpetas separadas dentro de `apps/admin/app/` para no chocar entre sí (nadie tocó `layout.tsx`, `page.tsx`, `middleware.ts`, ni ningún `package.json`; nadie corrió `pnpm install`, build completo, ni git):

- **Ventas + Domiciliarios**: listado real de `orders` (con lookup de `customers`/`couriers`), alta de venta manual con manejo inline de cliente (select de existentes + sección "cliente nuevo"), alta/listado de `couriers`.
- **Compras + Inventario + Proveedores**: alta/listado de `suppliers`, inventario de prendas en blanco con alerta visual de stock bajo y ajuste manual de stock, compras con generación automática de `inventory_movements` al marcar una compra como "recibida".
- **Bancos + Cuentas por cobrar + Cuentas por pagar**: cuentas bancarias + registro de transacciones (ingreso/salida), cuentas por cobrar/pagar con cálculo visual de "vencido" y total pendiente sumado.
- **Diseños**: banco de diseños con flujo de estado por botones contextuales (borrador → aprobación → aprobado → maquiladora → archivado), edición, y el toggle "Publicar en ecommerce".

Con eso, los 9 módulos del panel dejaron de ser placeholders — cada uno tiene listado real + formulario de alta conectado a Supabase.

## Integración después de los 4 agentes

- **Tipos reales de Supabase**: los 4 agentes reportaron el mismo problema — `packages/supabase/src/types.ts` seguía siendo el placeholder `Record<string, unknown>`, así que cada uno usó su propio workaround (`as any` en el cliente completo, `as never` en inserts, `as unknown as X[]` en selects) para poder compilar. Sin CLI de Supabase disponible (falta el access token), se escribió a mano un `Database` completo en `types.ts` a partir de `supabase/migrations/0001_init.sql` — las 17 tablas con `Row`/`Insert`/`Update`. Después se quitaron todos los `as any`/`as never` de los 9 módulos y se corrigieron los errores de tipo reales que aparecieron (principalmente: validar un `string` de un `<select>` contra el enum literal antes de insertarlo, con funciones `isXxx(value): value is Xxx` en vez de castear a ciegas). `pnpm build` queda limpio en ambas apps, 23 rutas en admin.
- **Hallazgo importante al probar en vivo**: al verificar las tablas reales con la `service_role` key, TODAS fallan con `403 permission denied for table x` (código Postgres `42501`). No es un problema de RLS ni de los agentes — es que `0001_init.sql` nunca le dio `GRANT` a los roles `service_role`/`authenticated`/`anon` sobre las tablas (RLS solo filtra filas, pero Postgres exige el `GRANT` de tabla primero, incluso para `service_role`). Se escribió `supabase/migrations/0002_grants.sql` con los `GRANT` que faltan + `ALTER DEFAULT PRIVILEGES` para que las tablas futuras los hereden solas. **Falta que el usuario la aplique** (mismo procedimiento: pegarla en el SQL Editor del Dashboard) — hasta entonces, el módulo admin compila pero no se ha podido probar en vivo contra datos reales.
- Se limpiaron dos artefactos que no debían commitearse: `apps/admin/tsconfig.tsbuildinfo` (caché de TypeScript) y `.claude/` (estado local del propio Claude Code, creado por un `ScheduleWakeup` de esta sesión) — ambos agregados a `.gitignore`.

- El usuario aplicó `0002_grants.sql` en el Dashboard de Supabase. Se verificó lectura Y escritura real contra las 17 tablas (insert + update + delete de una fila de prueba en `couriers`, borrada al final) — el módulo admin quedó confirmado funcionando de verdad, no solo compilando.

## Vercel: primer deploy fallido y corregido

El usuario conectó el repo a Vercel por su cuenta (proyecto para `@ricamo/admin`) y el primer deploy falló (`turbo run build` exitó con 1). El log mostraba advertencias de variables de entorno faltantes (`SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`), pero la causa raíz era otra: 5 páginas del admin (el dashboard `/`, `/ventas`, `/compras`, `/bancos`, `/domiciliarios`) no usaban ninguna API dinámica de Next.js, así que se generaban como páginas **estáticas** — lo que significa que `next build` ejecutaba `createServiceRoleClient()` durante el build mismo (fallando sin esas variables) y, más grave aún, habría dejado esas páginas sirviendo datos congelados del momento del build en producción, nunca datos en vivo.

Se agregó `export const dynamic = "force-dynamic"` a las 16 páginas del admin que consultan Supabase. Verificado localmente simulando la ausencia de esas variables (renombrando `.env.local` temporalmente) que el build ahora pasa igual. Se aclaró al usuario que además de este fix debe configurar las variables reales en Vercel (Settings → Environment Variables) para que el panel funcione en producción, no solo para que compile — incluyendo un tropiezo con el tipo "Secret" vs "Config" de Vercel para las variables `NEXT_PUBLIC_*` (esas deben ser "Config", no "Secret", porque de todas formas quedan visibles en el navegador).

## Módulo de Clientes, Campañas, Dashboard y Diseño→Producto (a pedido del usuario)

El usuario pidió: un módulo de clientes que sirva también para campañas de marketing y seguimiento de recompra, un dashboard general con métricas del negocio, y que la conexión diseño→producto de catálogo solo pueda pasar si el administrador la aprueba explícitamente. Se construyó todo en una sola sesión (sin agentes en paralelo esta vez, dado el tamaño más manejable y para evitar el overhead de integración de la ronda anterior):

- **`supabase/migrations/0003_crm.sql`** (nueva, aún sin aplicar): agrega `customers.city` y la tabla `marketing_campaigns` (nombre, asunto, mensaje, segmento objetivo, estado, destinatarios, fecha de envío), con sus GRANT explícitos.
- **`apps/admin/lib/metrics.ts`** (nuevo, no es una ruta): lógica compartida de clasificación de clientes por segmento de recompra (`sin_compras` / `nuevo` / `recurrente` / `inactivo`, este último si pasan más de 90 días desde la última compra) y formateadores de moneda/fecha, reusada por Clientes, Campañas y el Dashboard.
- **`apps/admin/app/clientes/`**: lista con segmento, pedidos, total gastado y última compra; ficha de cliente con historial de pedidos y edición; alta manual.
- **`apps/admin/app/campanas/`**: crear campaña (asunto + mensaje + segmento) en borrador; enviarla por correo vía Resend a los clientes con email que calcen con el segmento (envío secuencial, tope de 500 destinatarios, cada fallo individual no tumba el envío completo). Muestra un aviso si `RESEND_API_KEY`/`RESEND_FROM_EMAIL` no están configuradas.
- **`apps/admin/app/page.tsx` (dashboard) reescrito** con métricas reales: ventas totales, ingresos cobrados, ticket promedio, % de recompra, ingresos/salidas/balance de bancos, cuentas por cobrar/pagar pendientes, pedidos por estado, ítems de inventario en alerta, y cuatro rankings (top ciudades, top clientes, ventas por origen, gastos por categoría) con barras simples en CSS — sin agregar ninguna librería de gráficos nueva.
- **Diseño → Producto, solo con aprobación**: se reemplazó el viejo toggle "Publicar en ecommerce" (que solo marcaba un flag en `designs`, sin crear nada real) por un flujo donde un diseño en estado `aprobado` o `enviado_maquiladora` puede convertirse en un `product` de catálogo real vía `/disenos/[id]/publicar` (nombre, tipo de prenda, precio, primera talla) — validado también en el servidor, no solo ocultando el botón en la UI. Una vez creado el producto, publicar/despublicar alterna `products.is_published` (la fuente de verdad que ya lee el ecommerce) y sincroniza `designs.published_to_ecommerce`.
- Al escribir `disenos/[id]/publicar/actions.ts` aparecieron dos errores de tipo por narrowing de TypeScript que no habían salido en los módulos anteriores (una función `fail` local con closure sobre `designId`, y narrowing de un `string` a un literal atravesando un `while` con `await` adentro) — se resolvieron convirtiendo `fail` en una función de módulo con `designId` como parámetro (mismo patrón que ya usa `disenos/[id]/editar/actions.ts`) y capturando el valor narrowed en una constante aparte antes del loop.
- `pnpm build` limpio en ambas apps: 28 rutas en `@ricamo/admin`, todas dinámicas salvo `/icon.png` y `/_not-found`.
- **No se pudo verificar en vivo todavía** — falta que el usuario aplique `0003_crm.sql` (falla ahora mismo con "column customers.city does not exist").
